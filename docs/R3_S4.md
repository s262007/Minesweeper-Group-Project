## One command

```text
sbt "Test/runMain minesweeper.AutoPlay"
```

This writes `results/solver_stats.csv`: 1000 model games per 9x9 setting and player, and 25 hardware games per hardware size. It took 32 min on a laptop. For a shorter run, pass the counts and, optionally, the output file:

```text
sbt "Test/runMain minesweeper.AutoPlay 100 2 results/quick.csv"
```

## How a game is played

- **First click:** a random hidden cell. It is always safe (first-click protection), so it is not counted as a guess.
- **Then, while the game is running:**
  - reveal every safe hint;
  - if there is none, guess: reveal a random hidden cell that is not a mine hint.
- **Randomness:** the random number generator has a fixed seed per game, so a run is repeatable.
- **Flags:** the player never places any, since they do not change the hints.
- **Players:**
  - **v1 player:** follows the implementation's hints. MinesweeperCore builds the v1 Solver, so these are the hardware's hints, or the golden model's.
  - **v2 player:** follows `ModelSolver.solveV2`.

  `SolverCoSimTest` checks that the hardware v2 Solver gives the same hints as `solveV2` on played boards.
- **Shared layouts:** game i of a setting uses the same seed for every player and implementation, so all of them play the same mine layouts.

**Measures.** On each board where the player chooses a move (a "decision board"), the hints are compared with `SolverOracle`:
- the cells certain from the revealed numbers alone;
- the cells certain when the total mine count is also used.

v1 and v2 hints are both measured on the boards of the game being played. The counts are summed over decision boards, so a cell that stays certain over several boards counts on each of them.

**Model and hardware.** The hardware games run in lockstep with the golden model: every public field is compared after every command. The same games are then played on the model alone, and the two records must be equal. They are equal for all 50 hardware games.

## Results (`results/solver_stats.csv`, 10 November 2026)

| Grid, mines | Player | Games | Won | Won without guessing | Guesses per game | v1 finds | v2 finds | v1 / v2 with total |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 9x9, 10 (Beginner) | v1 | 1000 | 810 | 578 | 0.83 | 82.9% | 99.7% | 75.8% / 91.2% |
| 9x9, 10 (Beginner) | v2 | 1000 | 922 | 789 | 0.26 | 90.4% | 99.7% | 82.3% / 90.8% |
| 9x9, 14 (production default) | v1 | 1000 | 442 | 193 | 2.02 | 74.2% | 99.7% | 71.2% / 95.6% |
| 9x9, 14 (production default) | v2 | 1000 | 749 | 473 | 0.85 | 87.7% | 99.6% | 82.0% / 93.1% |
| 4x4, 3, hardware | v1 | 25 | 15 | 4 | 1.60 | 52.7% | 98.3% | 37.1% / 69.1% |
| 4x4, 3, model | v2 | 25 | 20 | 14 | 0.52 | 52.8% | 98.0% | 36.4% / 67.5% |
| 7x5, 6, hardware | v1 | 25 | 18 | 10 | 1.16 | 77.6% | 99.0% | 69.9% / 89.2% |
| 7x5, 6, model | v2 | 25 | 25 | 18 | 0.44 | 85.1% | 99.0% | 71.4% / 83.0% |

"v1 finds" and "v2 finds" are the share of the oracle's certain cells (from the numbers alone) that the hints give, on the decision boards of that row's games. The last column uses the cells certain with the total mine count instead. The CSV also has a model v1 row for each hardware size: it equals the hardware row.

What the numbers show:
- **v2 against v1.** On Beginner, v2 wins without guessing in 79% of games, against 58% for v1. Guesses per game drop from 0.83 to 0.26. With 14 mines the gap is larger: 47% against 19%, and 0.85 guesses per game against 2.02.
- **Pairs of clues are almost enough.** v2 finds 98 to 99.7% of the cells certain from the numbers alone. v1 finds 53 to 90%.
- **What remains.** The cells v2 misses need either the total mine count or reasoning on three or more clues. With the total, v2 finds 91 to 96% of the certain cells on 9x9, but only about 68% on 4x4, where the total decides many cells of so small a board.
- **Hardware solver time.** One solver run (v1) takes 25.8 cycles on average on 4x4 and 41.5 on 7x5. At 100 MHz that is well under a microsecond.
- **No search gave up.** The oracle finished on every decision board of the run (`oracle_gave_up` = 0).

## CSV columns

| Column | Meaning |
| --- | --- |
| `source`, `grid`, `mines`, `player` | Model or hardware, columns x rows, mine count, which hints the player follows |
| `games`, `won`, `lost`, `won_without_guessing` | Game counts. A game is won without guessing when no move after the first click was a guess |
| `guesses`, `guesses_per_game` | Guesses, in total and per game |
| `decision_boards` | Boards on which the player chose a move |
| `oracle_certain`, `found_v1`, `found_v2`, `v1_percent`, `v2_percent` | Cells certain from the numbers alone, and those given by the v1 and v2 hints, summed over decision boards |
| `oracle_certain_with_total`, `v1_percent_with_total`, `v2_percent_with_total` | The same with the total mine count |
| `oracle_gave_up` | Decision boards on which the oracle went over its budget; they are left out of the counts |
| `hw_solver_cycles_mean` | Hardware rows only: mean `solverCycles` of the commands that ran the solver |

## Test in CI (`AutoPlayTest`)

The test runs 30 model games per 9x9 setting and player, and 2 hardware games per size, in 1 min 23 s locally. It checks:
- the row order;
- that each hardware game equals the same game on the model;
- on every game: v1 finds no more than v2, v2 no more than the oracle, and the oracle no more than the oracle with the total;
- that a game without a guess is always won;
- that the CSV has one line per row and the same number of columns on every line.

## Not covered

- The hardware games use the v1 Solver, the one MinesweeperCore builds. The v2 numbers come from `ModelSolver.solveV2`, whose hints `SolverCoSimTest` checks against the hardware v2 Solver.
- Hardware games stop at 7x5: a 9x9 hardware game would take minutes with the default simulator.
- "Won" includes wins after a lucky guess. The player guesses uniformly, without probabilities.
