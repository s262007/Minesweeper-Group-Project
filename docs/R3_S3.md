## Exact oracle

`SolverOracle.certain(grid, clues, totalMines = None)` returns the cells that have the same value, safe or mine, in every mine layout that fits the revealed numbers. Flags are not inputs: they are player notes, not facts.
- **Frontier:** the unknown cells next to at least one clue. Clues that share an unknown cell join their cells into one component.
- **Search:** each component is searched by backtracking. A value is tried for a cell only if each of its clues can still be met: not more mines than the number, and enough open cells for the rest. Cells are ordered by a breadth-first walk over shared clues, so a clue's cells are close together and its count is checked early.
- **Interior:** the unknown cells next to no clue. The clues say nothing about them, so they are decided only when `totalMines` is given.
- **Total count:** with `totalMines`, a component's mine count is kept only if the other components and the interior can hold the rest.
- **Result:**
  - `Exact(safe, mine, ...)` when the search finishes;
  - `Inconsistent` when no layout fits;
  - `GaveUp` when the search tries more than 2^20 cell values. In that case it claims nothing.

ModelSolver (v1 and v2) and the hardware Solver use local rules. Each of their hints must therefore be in the oracle's answer, but they may miss certain cells.

### Oracle tests (`SolverOracleTest`, 8 tests, about 11 s)

| Test | What it checks |

| Inconsistent clues | Three boards that no layout fits |
| Enumeration | 400 random boards up to 5x5 with at most 12 hidden cells. One board in five gets a wrong number. Each board is tested without a total, with the true total and with a total off by one. The result must equal a separate check that tries every layout, including on boards no layout fits |
| Played games | 635 boards from model games (9x9 and 6x5): every certain cell agrees with the true layout; the total never removes a certain cell; every ModelSolver v1 and v2 hint is in the oracle. The oracle finds more than v2 on 11 boards, and the total adds cells on 64 |
| Budget | 3x60 with the middle row revealed (one component of 120 cells, about 2^30 layouts): `GaveUp` in under a second. A board solved with the default budget gives `GaveUp` under a budget of 20 |

## Property tests (`PropertyTest`)

### Generators (ScalaCheck)

- **Capacities:** rows and columns from 2 to 9, sometimes with a second, smaller preset, so that the active grid leaves padding.
- **NewGame:** a preset, a legal mine count (the minimum, the maximum or in between) and a seed from 1 to 0xffff.
- **Moves:**
  - always a first click;
  - then up to 2 × cells moves for the model, or 7 for the hardware.
- **Kinds of move:** some name a coordinate inside the storage (reveal or flag). The others are resolved when played:
  - reveal a safe hidden cell;
  - reveal a cell with a safe hint;
  - reveal any hidden cell (it may be a mine);
  - flag a hidden mine.
  The first and last use the private layout, as in simulation-only checks (CONTRACT 7).
- Moves after the end of a game are kept, because they must be no-ops.

### Properties checked after every command

The checks read only the public view and the true layout. They share no code with the model's cascade or solver, nor with the hardware.

1. **State:** a completed command on a real game ends in Idle, Playing, Won or Lost, never Error or InternalError.
2. **Active grid:** the active cells are exactly the active grid; padding cells are blank.
3. **Revision:** it goes up by one exactly when `changed` is set. A command that changes nothing (a no-op or a Range error) leaves the whole view unchanged.
4. **Mine counter:** `minesLeft = mines - flags`.
5. **Numbers:** every revealed number is a safe cell and shows its true count.
6. **Mines and explosion:** mines are visible only after a loss, and then all of them; `exploded` is set exactly when the game is lost.
7. **Win:** the game is Won exactly when every safe cell is revealed.
8. **Hints:**
   - they are only on unrevealed cells, never both safe and mine, and true for the layout;
   - each hint is in the oracle's certain cells;
   - there are no hints while `hintsValid` is low, and Playing always has valid hints.
9. **NewGame:** it clears the board, flags, hints, the explosion and the layout.
10. **Reveal:**
    - revealed cells stay revealed;
    - the new cells are exactly a breadth-first search from the click through cells with no mine around them, stopped by revealed and flagged cells;
    - `revealLayers` is that search's number of layers;
    - a losing click reveals nothing else, and the clicked mine is `exploded`.
11. **Flag:** it toggles that cell only, reveals nothing, and leaves the hints unchanged (CONTRACT 7: user flags do not change deductions).
12. **Finished game:** reveals and flags after Won or Lost change nothing.

The hardware run is slow because the default simulator takes about 0.2 s per clock cycle on this design. In one run, 568 cycles took 122 s; the slowest game used 139 cycles and took 29 s. Its time depends on how many cycles the generated games need. CI ran about three times faster than this laptop on the last runs, so the file should stay under the story's 3-minute CI budget.

Five local runs (2,100 model games and 56 hardware games) found no property failure.

### When a property fails

The report gives:
- the broken properties;
- the generated `MsParams` and `GameScript`;
- the commands played;
- the mine layout;
- the board before and after the command.

To keep a failure as a named regression test, paste the two values:

```scala
it should "keep <property> on <case> (regression)" in {
  val p = MsParams(...)                 // from the report
  val model = new GoldenModel(p)
  GameProperties.play(GameProperties.GameScript(...), model, cmd => cmd.run(model), () => model.snapshot)
}
```

For the hardware, run the same script through `Lockstep`, as in the hardware run.

## Findings and mutation checks

**Finding.** The enumeration test found one bug, in the first version of the oracle:
- It built a Scala `Map` from pairs (always-mined cells, sometimes-mined cells), one pair per mine count. Two counts with no always-mined cell merged into one entry, so a cell that is a mine in some layouts came out safe.
- It was fixed before the first commit.
- It is kept as a named regression test.

**Mutation checks.** Not committed. Each one was injected in `GoldenModel`, run against the model property test, and reverted (the file was restored from a copy and checked with `git diff`):

| Injected bug | First message |
| --- | --- |
| The cascade also expands from numbered cells | "mine shown as a number" (and the solver reports a contradiction) |
| Won declared one safe cell too early | "state Playing while all safe cells revealed = true", on a game with no mines: the mutated rule misses the real win |
| No solver run after a flag | "Playing without valid hints" |

## Not covered

- Production sizes on hardware: the hardware run uses a 6x5 build, because a 30x24 game takes hours with the default simulator.
- `GaveUp` boards: on those the hint check is skipped. It never happened on the small boards of these tests.
- Independence: the same assistant wrote the hardware Solver, the golden model, the oracle and these checks. The checks are written from the contract and share no code with the model or the hardware, but R3's review is still needed.
